How fast the package encodes and decodes, next to Apache Avro for Java and fastavro, on the same schemas and the same values. These are the numbers of one run on one machine: a guide to the size of the differences, not a promise for yours.

  • Before: binary record encode and decode took 9.5× to 14.4× as long as Java's. The codec walked the schema for every value.
  • After: they take 1.2× to 1.9× as long as Java's, 5 to 10 times as fast as before. The codec compiles the writer schema once, at the first encode or decode.
  • Unchanged: decoding with a reader schema that differs (resolve) still walks the resolution, and takes about 12× to 16× as long as Java's; it was outside the target. JSON and container files are faster because they use the binary codec underneath.
  • Margin: the closest case is interop/encode at 1.88×. Runs of the same build differ by about 10% between processes, on the Java side up to 2× in single cases. Each column is one run.

The cases

Every workload is encoded (encode), decoded with the writer schema (decode), and decoded with a reader schema that differs (resolve). The three programs load the same schema files and build the same values, whose encodings were checked to be byte for byte the same on all three sides.

Workload Value Reader schema of resolve
interop One record of Apache's interop.avsc, with a nested Node, 103 bytesint and float promoted, a field dropped and one added
envelope The envelope of an AXT example messageformat as long, a field added
wide 50 fields of 10 kinds, 234 bytes The fields in reverse order, int and float promoted
longs An array of 10,000 longs, 59,691 bytesAn array of double
  • json/…: Avro's JSON encoding of the interop and wide values. fastavro's JSON encoder does not end on the recursive Node, so it has no json/interop cases.
  • file/<compression>/write and read: a container file of 1,000 wide records in memory, with blocks of 64 KiB; deflate at level 6 and zstandard at level 3 on every side.
  • typed/envelope/…: TypedCodec with a generated class. Java would need its own code generator and fastavro has none, so they have no such case.
  • Java decodes strings as Avro's lazy Utf8, its default; this package decodes them into Dart Strings, which costs more.

Repeating the runs

The programs are in tool/bench of the repository, and docs/benchmarks.md has every detail of the cases and how each side measures. From the repository root: 

# Dart, compiled ahead of time
dart compile exe tool/bench/bench.dart -o /tmp/bench
nice -n 19 /tmp/bench --json dart.json

# Java
(cd tool/bench/java && mvn -q -T1 package dependency:copy-dependencies)
nice -n 19 java -cp 'tool/bench/java/target/classes:tool/bench/java/target/dependency/*' \
  bench.Bench --json java.json

# fastavro
python3 -m venv /tmp/venv
/tmp/venv/bin/pip install 'fastavro[snappy,zstandard]==1.13.1'
nice -n 19 /tmp/venv/bin/python tool/bench/fastavro_bench.py --json fastavro.json

Each prints a table of operations per second, µs per operation and the size of the encoding per case; --json also writes it to a file. The comparison is a script to repeat, not a CI gate: CI runners are too noisy for it.
